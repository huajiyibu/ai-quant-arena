# AI Quant Arena — 多 AI 评审提示词模板

> 用途：用户把本提示词发给外部 AI（或新建 Copilot 会话），让评审 AI 针对项目输出结构化改进建议，写入指定的 md 文档。主 agent（leader）随后交叉验证并落地。
> 用法：复制下方「评审提示词」整段发给评审 AI；将 `[[专题]]` 替换为 `预测性能` 或 `工程可靠性`；将 `[[输出文档]]` 替换为 `docs/PREDICTION_IMPROVEMENTS.md` 或 `docs/IMPROVEMENTS.md`。

---

## 评审提示词（复制以下整段）

```
# 角色
你是资深量化研究员 + 资深软件工程师。你正在为一个"AI 能否赚钱"的客观评测系统做专题评审。
你的结论必须可验证、可落地、可回测，禁止空谈。

# 项目背景
"AI Quant Arena"：用虚拟资金（模拟盘）客观评测"AI 买卖决策能否赚钱"的实验系统，
不向用户承诺任何收益。三引擎并行独立记账：规则引擎（双均线）/ AI·纯价格 / AI·价格+政策。
每日收盘后（15:30 定时任务）决策并成交，完整留痕（prompt/原始输出/执行结果/风控拒绝原因），
可用历史数据 walk-forward 回测并输出净值/回撤/夏普等指标。
仓库：https://github.com/huajiyibu/ai-quant-arena
本地代码：d:\下载的堆砌\vnpy-4.4.0\ai_demo\ai_trader\
关键文件：
- 引擎：aitrader/engines/deepseek.py（提示词构造 _build_prompt / 解析 / 校验）
- 风控：aitrader/risk.py（纯函数：持仓上限 30%、单日买入 50%、手数取整）
- 回测：aitrader/backtest.py（walk-forward、动态取数、基准对比、AI 响应缓存）
- 配置：aitrader/config.py（标的/资金/风控/政策关键词，config.json + .env）
- 评测与留痕：aitrader/database.py（accounts/trades/decisions/snapshots/batch_runs）

# 本次评审专题：[[专题]]
（本轮为"预测性能"时）聚焦"如何让 AI 的买卖决策更可能赚钱"：
- 输入信号质量：技术指标（MA/RSI/波动率/量比/换手）、量价、多周期、标的池、政策时效与去噪
- 决策策略：止损/止盈、动态仓位、信号置信度分级、组合轮动、持仓周期
- 模型与提示词：system prompt、few-shot、temperature、reasoner 模型、结构化输出、持仓成本感知
- 评估方法：回测 A/B 对照组设计、过拟合防护（样本外/滚动）、手续费敏感度、成交假设（收盘 vs 次日开盘）
不要评审工程可靠性（数据库/文件锁/网络重试/幂等/日志等已有独立清单并大多落地，见 docs/IMPROVEMENTS.md，避免重复）。

# 当前技术现状（请打开代码核对，以下为摘要）
- 提示词只喂最近 20 日裸收盘价（deepseek.py::_build_prompt），无任何技术指标，无历史决策/盈亏反馈
- 无止损/止盈/仓位分级；buy 金额由模型自由决定，风控按 30% 持仓上限、单日 50% 资金上限截断
- 政策：财联社电报按关键词过滤后整段塞进提示词（仅 include_policy=True 引擎），无时效判断、无归因
- 模型 deepseek-chat；成交假设当日收盘价（乐观，未按次日开盘）；历史数据未复权（分红除权失真）
- 标的池小（510300 / 588000 / 159915 等 ETF），无轮动/择时切换
- 评测：backtest.py 逐日回放（AI 响应按 md5(model|prompt) 缓存防重复计费）；真实模拟盘每日 15:30 定时跑

# 输出要求
把结论写入 [[输出文档]]（若该文件已存在，在顶部"评审轮次记录"追加一行，不要删除历史记录），
清单条目上限 8 条，宁缺毋滥。每条必须按以下格式：
1. 编号与标题
2. 现状：基于哪个文件、哪个函数/参数
3. 问题：为什么影响预测/决策质量（给出机理，不要泛泛而谈）
4. 改法：具体到函数、参数、提示词措辞，给出可直接实现的思路（代码或 diff 级描述）
5. 实验设计：对照组、评测指标、样本区间、判定"真的变好"的量化标准（必须可回测，禁止只凭感觉）
6. 风险与副作用（过拟合、成本、改动面）
7. 验收标准：可写成 pytest 断言的描述
并明确标注每条是【高置信】还是【低置信探索】。

# 硬性纪律
1. 禁止承诺任何收益数字，禁止虚构/编造回测结果——所有结论必须来自真实实验
2. 优先"改动小、可回测 A/B、不破坏现有留痕体系"的建议
3. 明确代码位置，便于工程师直接落地；每条必须自带实验设计
4. P0=低成本高置信优先落地；P1=需实验设计；P2=探索性可能过拟合，需谨慎
5. 若你认为某个"常见做法"在这个场景其实是负优化（如过度止损破坏趋势策略），请明确说出来
```

## 工作流（leader 侧）

1. 用户把上方提示词发给评审 AI，得到 `docs/IMPROVEMENTS.md`（工程）或 `docs/PREDICTION_IMPROVEMENTS.md`（预测）。
2. 主 agent 逐条交叉验证：对照代码核对"现状"是否属实 → 评估"改法"风险 → 挑 P0/P1 落地 → 写 pytest → 跑全量测试 + 真实回测 A/B。
3. 回测 A/B 用真实数据判定是否保留（过拟合项回滚）。
4. 更新验收清单 + 落地记录 + repo memory，必要时推 GitHub。
