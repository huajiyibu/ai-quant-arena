# 体检方向 01：架构与代码质量（诊断结果）

> 体检日期：2026-08-13　视角：量化系统架构师 / 代码质量评审专家　手段：终端逐行读真实磁盘代码（`aitrader/` 全部 `.py` + `run.py`）+ Pylance 全工作区诊断 + `docs/IMPROVEMENTS.md` 历史评审对照。基线：v0.22（HEAD=`44be281`），197 pytest。

## 1. 结论摘要

1. **模块边界与依赖方向整体健康**：`config → models → portfolio/risk → database → batch/backtest → reporter/run` 单向依赖、无循环；portfolio/risk/features/attribution 坚持纯函数、`AccountState` 不可变；引擎与数据源有抽象（基类 / Protocol / Fake），成熟度高于同类小项目。
2. **两个"上帝模块"是最大的架构债**：`run.py`（657 行 / 23 个 CLI 参数 / 7 类职责）与 `reporter.py`（453 行 / 绘图 + HTML + 文本三合一，CSS 双份重复），任何新需求都要动它们，单测成本高、接口面失控。
3. **存在一批真实的技术债**：批处理写路径非原子（无 `transaction()` 抽象）、`portfolio.py` 类型注解引用未导入的 `RiskConfig`/`datetime`、`attribution.py` 保留 dict/Trade 双类型兼容分支、`datasource.py` 导入即全局 monkey-patch `socket`、多处 `except: pass` 静默吞异常、魔法数字/标签枚举/佣金率散落重复。

## 2. 问题清单

### 🔴 P0-1 批处理写路径非原子，且 decisions 无唯一约束——崩溃窗口会重复决策留痕

- **现象**：`_run_engine` 的 `begin_batch_run → add_trade×N → save_state → add_snapshot → complete_batch_run` 逐条独立连接写入、无事务包裹；`Database` 没有任何 `transaction()` / `BEGIN/COMMIT` 抽象。v0.20 已给 `trades` 加唯一约束 + `INSERT OR IGNORE` 使**资金层**幂等，但 `decisions` 表是普通 INSERT、无 UNIQUE → 崩溃后重跑会**重复插入决策留痕**，污染 Rank IC 校准 / 归因 / 复盘。
- **证据**：`batch.py` L333 `begin_batch_run` → L341 `add_trade` → L351 `save_state` → L353 `add_snapshot` → L364 `complete_batch_run`；`database.py` 全文件 grep 无 `transaction/BEGIN/COMMIT`（写方法各自 `with self._connect()`）；`_SCHEMA` 中 `decisions` 无 UNIQUE；`database.py::add_decision` 为普通 INSERT；`docs/IMPROVEMENTS.md` 明确"完整 `transaction()` 包裹留作后续加固"（P0-4 未落地）。
- **影响**：无人值守下断电/崩溃重跑会得到重复决策样本，评测（Rank IC、归因、复盘）失真；对账时资金与留痕可能不一致。
- **修复建议**：给 `Database` 增加 `transaction()` 上下文管理器，把 `_run_engine` 写路径整体包进一个事务、任一环节失败整体回滚；短期至少给 `decisions` 加 `UNIQUE(account_id, date, symbol, action, fallback)` + `INSERT OR IGNORE`。

### 🟡 P1-1 `run.py` 上帝模块：657 行、23 个 CLI 参数、7 类职责混杂

- **现象**：CLI 解析与校验（`_date_type`）、引擎工厂（`build_engines`）、引擎过滤（`select_daily/backtest_engines`）、补跑计算（`_catch_up_dates`）、回测编排（`run_backtest`）、批处理编排（`_run`）、告警通知（`_maybe_notify`）、`last_run` 记账（`write_last_run`）、日志（`setup_logging`）、单实例锁全部挤在一个文件。
- **证据**：`run.py` 共 657 行；argparse 参数 L395~L481 共 23 个；`main` L392 / `_run` L501 / `run_backtest` L240 / `build_engines` L107 / `_maybe_notify` L618 / `write_last_run` L70 / `_catch_up_dates` L213 / `setup_logging` L45。
- **影响**：任何新模式/参数都要动此文件；`run_backtest`（L240~L390，约 150 行）与 `_maybe_notify`（L618~L655）都是重量级函数；23 个 CLI 参数已从"用户入口"退化为"程序员的实验开关面板"，README/help 维护成本高。
- **修复建议**：按职责拆 `cli.py`（解析）、`engine_factory.py`、`backtest_runner.py`、`notify.py`（含 `_maybe_notify`）、`batch_runner` 已独立；大量 A/B 实验参数收敛到 config 或 `--config-override key=value`，CLI 只留高频操作。

### 🟡 P1-2 `reporter.py` 职责混杂：绘图 + HTML + 文本汇总 + 口径计算，CSS 双份重复

- **现象**：绘图（`plot_compare`/`plot_backtest_curves`）、HTML 日报（`build_daily_report`/`build_backtest_report`）、CLI 文本（`build_summary`）、公平口径计算（`_fair_pnl`/`_true_pnl`/`_fair_snapshots`）全在一个 453 行文件；两份 HTML 各自内联**几乎相同的 CSS**（body/card/green/red/img/foot）。
- **证据**：`reporter.py` 函数 L41/L95/L120/L314/L387；`<style>` 出现两处 L288 与 L431；`build_daily_report` 的基准拉取 `ds.fetch_daily_bars(first_sym, 500, ...)` L265 硬编码 500 根。
- **影响**：日报新增指标要同时改 Python 与两份 CSS；绘图与 HTML 强耦合无法单独复用；基准取数 500 根硬编码 + 实时联网 + 失败静默（详见 P1-5）。
- **修复建议**：拆 `plots.py`（绘图）、`report_html.py`（HTML + 共享 CSS 常量或模板文件）、`summary.py`（文本）；基准改用本地 `bars` 表 + 动态窗口（衔接 IMPROVEMENTS P1-10）。

### 🟡 P1-3 `datasource.py` 导入即改全局 socket 行为（monkey-patch + setdefaulttimeout）

- **现象**：模块顶层直接执行 `socket.setdefaulttimeout(15)`（L9）并替换全局 `socket.getaddrinfo`（L14~L27 `_ipv4_first_getaddrinfo`）。任何 `import aitrader.datasource` 的进程（含测试、其它脚本）都被静默改变网络行为；`setdefaulttimeout` 影响进程内**所有** socket（不止行情域名）。
- **证据**：`datasource.py` L9、L12~L27（模块导入即执行，无函数包裹）。
- **影响**：隐式全局副作用、跨模块/跨测试不可见；若未来引入其它网络库/异步客户端会莫名受 15s 超时约束；monkey-patch 拦截所有域名解析有兼容性风险（例如在库代码中被覆盖或与其它 patch 冲突）。
- **修复建议**：把超时与 IPv6 处理下沉到具体网络调用处（自建 `requests.Session` 或统一 `_http_get` 辅助函数），或用显式 `init_network_hacks()` 替代导入副作用。

### 🟡 P1-4 遗留 dict/Trade 双类型兼容分支 + 配对算法重复实现

- **现象**：`closed_trade_pairs` 同时接收 `database.get_trades` 的 dict 记录与 `execute_decisions` 的 `Trade` 对象，用 `_f`/`_d` 两套字段访问兜底；而 `attribute_trades` 只认 dict。同一套"FIFO buy→sell 配对 + 净佣金口径"逻辑在两个函数各写一遍。
- **证据**：`attribution.py` L76 `_f(t, key) = t[key] if isinstance(t, dict) else getattr(...)`、L79 `_d(v)`；L20 `attribute_trades` 与 L64 `closed_trade_pairs` 配对逻辑重复。
- **影响**：调用方类型不统一导致维护时"改了 dict 版忘了 Trade 版"；新增字段/改口径容易漏改一边，属典型的类型债。
- **修复建议**：统一调用方传 dict（database 已返回 dict，`Backtester._trades_so_far` 的 Trade 列表改为先转 dict），删掉兼容分支；把配对算法抽成单一纯函数，归因与复盘共用。

### 🟡 P1-5 多处静默吞异常，失败不可见

- **现象**：日报基准对照失败 `except Exception: bench_line = ""` 完全静默（用户无法分辨"没有基准"还是"拉取失败"）；`notify.py` 两段 `try: ... except Exception: pass`；`datasource._fetch_realtime` 失败仅 warning 返回 None。
- **证据**：`reporter.py` L273 `except Exception: bench_line = ""`；`notify.py` L62/L73 `except Exception: pass`；`datasource.py` L154/L188。
- **影响**：无人值守下"坏数据被当作没有数据"悄悄发生；`last_run.json` 仍 `ok=true`，告警链条难覆盖这类静默降级（05 号体检发现的"主库被清空而 last_run 仍 ok"即同型问题）。
- **修复建议**：降级处至少 `logger.warning`，并在报表/CLI 显式标注"基准获取失败（原因）"；`notify` 失败记录原因到本地日志。

### 🟡 P1-6 魔法数字 / 业务常量硬编码且多处重复

- **现象**：
  - 标签枚举"趋势/回调/政策/超买/超卖/其他"在 `deepseek.py::_system_prompt`（L84）与 `_build_prompt` 输出契约（约 L287）、`attribution.py` 注释三处重复；
  - 佣金率 `0.00025` 在 `config.py` 默认值与 `attribution.py` L20/L64 默认参数重复；
  - `FAIR_START_DATE = "2026-08-10"`（`reporter.py` L13）业务口径日期写死代码；
  - 回测 `timedelta(days=120)`（`run.py` L299）、`MAX_CACHE_ITEMS=2000`（L281）、取数上限 `5000`（L337）、基准 `500` 根（`reporter.py` L265）、`252` 交易日、rule 买入比例 `0.3`（`rule.py` L32）。
- **证据**：见上各文件:行号。
- **影响**：改口径要搜多个文件，易漏改导致"回测与真实盘口径漂移"（历史上 P2-13 默认值漂移已真实发生过）；标签枚举若前后不一致会让归因把标签归入"其他"。
- **修复建议**：标签枚举、佣金率、交易日数等收进常量模块或 config；`FAIR_START_DATE` 这类口径日期集中定义并注释变更原因；rule 引擎的 `0.3` 改读 `risk.max_position_pct`。

### 🟡 P1-7 `portfolio.py` 类型注解引用未导入符号（靠 `__future__` 侥幸不崩）

- **现象**：`apply_stop_rules(state, ..., risk: RiskConfig)`（L84）与 `execute_decisions(..., trade_date: datetime)`（L113）的注解用了 `RiskConfig`/`datetime`，但文件顶部只 `from .models import AccountState, Decision, Position, Trade`。
- **证据**：`portfolio.py` L7 import；L84/L113 注解；Pylance 工作区诊断报 `未定义"RiskConfig"`（L84/L112）与 `未定义"datetime"`（L113）。
- **影响**：依赖 `from __future__ import annotations` 惰性求值才不崩，类型检查/IDE 报错、mypy/pyright 不可用，注解形同虚设；一旦有人改静态求值即运行时崩溃。
- **修复建议**：补 `from .config import RiskConfig` 与 `from datetime import datetime`。

### 🟢 P2-1 一批未使用参数/导入（Pylance 全量诊断确认）

- **现象**：未使用参数：`run.py::_catch_up_dates` 的 `settings`（L213）、`batch.py::_calibrate_forward_returns` 的 `date`（L142）、`reporter.py` 的 `plot_compare`/`build_summary`/`plot_backtest_curves`/`build_backtest_report` 的 `settings`（4 处）、`datasource.py::FakeDataSource.fetch_daily_bars` 的 `exchange`/`adjust`、`FakePolicySource.fetch_macro_news` 的 `decision_date`/`cutoff_time`；未使用导入：`backtest.py` L19 `AccountState`、`batch.py` L16 `AccountState`、`datasource.py` L8 `time`。
- **证据**：Pylance `workspace/diagnostic` 逐条对应（severity=4 未存取）；`features.py` L35 `lookback` 参数为"预留兼容参数"，从未使用。
- **影响**：接口签名失真（调用方以为参数生效实则无效），误导后续维护；每处未用参数都是潜在的"本应传但没传"的坑。
- **修复建议**：删除或改名 `_settings`/`_date` 并在 docstring 注明兼容意图；`lookback` 若确无用途可移除或按"未来特征窗口上限"补真实实现。

### 🟢 P2-2 测试文件按版本号累积（test_v02~v22 共 21 个），且 reporter/database/notify 无专门测试

- **现象**：`tests/` 下 32 个文件，其中 21 个是 `test_vXX.py`（每个迭代版本一个），命名按迭代而非被测模块；`reporter.py`/`database.py`/`notify.py` 无独立测试文件（相关覆盖散落在 test_vXX 里）。
- **证据**：`tests/` 目录列表（test_v02.py~test_v22.py 21 个 + 11 个按模块命名）。
- **影响**：新人不看历史版本号无法定位"这个行为测在哪"；测试随版本持续膨胀；各模块被测程度不可一眼看出；reporter 这类最易回归的展示层反而覆盖最散。
- **修复建议**：按被测模块重组（`test_reporter.py`/`test_database.py`/`test_notify.py`），版本历史用例并入模块文件或标注出处；新用例按模块落位。

### 🟢 P2-3 扩展性：引擎/数据源有抽象，存储层无抽象；引擎名常量散落

- **现象**：`DecisionEngine` 基类 + `build_engines` 工厂、`DataSource`/`PolicySource` Protocol + Fake 实现，新增引擎/数据源成本低；但 `Database` 是 sqlite 专属实现、无 Repository 接口，换存储需整体重写；引擎名 `"rule"/"ai"/"ai_policy"` 字符串在 `run.py`（L395 choices、L107/142/168/618）多处硬编码。
- **证据**：`engines/base.py` L42 `DecisionEngine`；`datasource.py` L39/L246 Protocol；`database.py` L136 sqlite 专属；`run.py` 引擎名字符串多处。
- **影响**：新增引擎（如 ml）低、新增存储（如换 PG）高；引擎名拼错只在运行时发现（如 `_maybe_notify` 遍历 `engines` 时按 key 查账户）。
- **修复建议**：存储层提 `Repository` 接口；引擎名统一引用 `models.EngineType` 常量。

### 🟢 P2-4 idle 告警用日历天近似交易日 + 空仓误报

- **现象**：`_maybe_notify` 用 `cutoff = date - timedelta(days=n*2)` 近似 N 个交易日（长假/周末偏差大）；`check_alerts` 对 `trades_count == 0` 无条件告警，本来就空仓的保守策略持续误报。
- **证据**：`run.py::_maybe_notify`（L618 附近 cutoff 计算）；`notify.py::check_alerts` L31 `if trades_count == 0`。
- **影响**：告警噪音，可能掩盖真实异常；目前因 notify 关闭暂无症状，开启即暴露。
- **修复建议**：用 `is_trading_day` 统计最近 N 个交易日成交；区分"有持仓但无成交"（真异常）与"本来空仓"（降级为提示）。

### 🟢 P2-5 `build_engines` 中 DeepSeekEngine 构造参数重复传两遍

- **现象**：ai 与 ai_policy 两个引擎构造时把 `api_key/base_url/model/lookback/max_buy_count/temperature/system_prompt_extra/feature_inject/market_env_inject/feedback_n/response_cache` 十几个参数各写一遍，ai_policy 仅多 `include_policy=True`/`name`。
- **证据**：`run.py::build_engines` L107~L140。
- **影响**：新增参数要改两处、易漏；复制粘贴痕迹明显。
- **修复建议**：抽公共 kwargs dict 或共享默认配置对象，两引擎差异只保留 `include_policy`/`name`。

## 3. 做得好的地方

1. **分层与依赖方向清晰、无循环**：`config→models→portfolio/risk→database→batch/backtest→reporter/run` 单向依赖；portfolio/risk/features/attribution 坚持纯函数、`AccountState` 不可变（每次变更返回新对象），可测性与审计性兼备。
2. **可观测性投入扎实**：决策全量留痕（prompt/raw_output/validation/execution_result）、`last_run.json` 失败保留上次正常、单实例锁 + 双层幂等（快照 + batch_runs + trades 唯一约束）、`retry_call` 指数退避覆盖行情/实时/政策/分红/AI 四条网络链路，且多落盘路径用了 `tmp + os.replace` 原子写（AI 缓存）。
3. **引擎/数据源抽象到位**：`DecisionEngine` 基类 + `DataSource/PolicySource` Protocol + Fake 实现 + 可注入 HTTP 客户端，新增引擎/数据源/测试替身成本低；DeepSeek 缓存键含 `model|temperature|system|prompt`，改配置不误用旧缓存，并做了进程内 API 调用/命中计数。

---

## 4. 一句话总结

**模块分层、纯函数设计、留痕与幂等功底都超过同类小项目，但 `run.py`/`reporter.py` 两个上帝模块、批处理写路径非原子、以及一批死代码/类型/硬编码债，决定了它"每天能自动跑"很稳、"长期可持续演进"仍需一次收敛职责与补齐事务抽象的架构整理。**
