# 体检方向 05：运维与稳定性（诊断结果）

> 体检日期：2026-08-13　视角：量化系统 SRE / 运维专家　手段：只读代码 + 真实日志 + `schtasks` + 数据库只读核查

## 1. 结论摘要

1. **"每日必跑"核心链路基本可靠**：计划任务 15:30 每交易日正常执行（08-10~08-13 `Last Result=0`），单实例锁 + 同日幂等（`batch_runs` 只认 `done` + `has_snapshot` + trades 唯一约束）使多次同日并发运行均正确跳过、**零重复成交**；收盘守卫/日历降级/行情硬校验均有真实日志佐证。
2. **但"自愈"与"可观测"两翼缺失，且与提示词描述不符**：`--catch-up` 在两个自动入口（计划任务 **和** 登录启动项 `.lnk`）**实际都未接线**（提示词称"已接"）；`notify.enabled=false` 使整条告警链路**处于关闭状态**（连已修复的 P0-3 回撤告警也发不出）；无 `--health`、无 API 成本累计。
3. **真实主库账本在 08-13 被"全量重置重来"（用户 08-13 的有意决定：`reset_account` 三账户 + 清 `batch_runs`，历史备份在 `aitrader_backup_20260813_1630.db`）**——重置本身合理，但**系统对"账本连续性中断/重置"零感知**（`last_run.json` 仍 `ok=true`、无 `--health`、无告警），且 `.lnk`/计划任务均未接 `--catch-up`，重置后无任何"新账本从干净状态起步"的自检。

## 2. 问题清单

### 🔴 P0-1 账本重置后系统零感知、无连续性监控（重置本身为 08-13 用户有意决定）

- **现象**：`data/aitrader.db` 当前为"空账本"（3 个账户初始状态、现金各 100 万、空仓、`last_interest_date=NULL`），但 `last_run.json` 显示 08-13 15:30 正常跑批并产出资产结果，二者矛盾——**无人值守系统对此无任何感知/告警**。
- **证据**：
  - 已核实：08-13 用户决定"全量重置重来"（`reset_account` 三账户 + 清 `trades/decisions/daily_snapshots/batch_runs` + 状态回 100 万 + 清 `last_interest_date`），备份在 `aitrader_backup_20260813_1630.db`（含 17 快照 08-07~08-13、50 决策、7 成交、12 条 `batch_runs` 全 `done`）；
  - `data/aitrader.db`（LastWriteTime=`2026/8/13 16:53:36`）：`snapshots=0`、`decisions=0`、`trades=0`、`batch_runs=空`；`check_daily.py` 实跑输出全空；
  - `last_run.json` 仍为 `2026-08-13T15:30:15 ok=true` —— **重置后无人复核，系统也永远不会告知"账本被重置"**。
- **影响**：重置是有意的，但这是**无人值守下的高风险操作**——若为误操作/他人操作，无任何拦截与告警；净值曲线/成交/决策/Rank IC 历史依赖单一备份库（`aitrader_backup_20260813_1630.db`），备份策略无轮转/无自动校验。
- **修复建议**：① 重置/换库走显式流程（脚本 + 日志 + 备份命名带原因时间 + 执行前确认），禁止静默替换；② `--health`（P1-2）增加"账本连续性"检查（最近快照日期 vs 交易日历、连续缺失 N 天 → 告警 + 非 0 退出码），让"账本被重置/长时间无快照"可被自动发现；③ 备份策略升级（保留最近 N 份、重置前自动快照）。

### 🔴 P0-2 N-9 `--catch-up` 在真实部署中完全空转（`.lnk` 参数漂移）

- **现象**：无人值守的两个自动入口都没有 `--catch-up` 参数。计划任务 15:30 **裸跑 `run.py` 是 v0.17 的既定设计**（当天由定时任务处理，漏跑靠登录启动项补）；但**登录启动项 `.lnk` 实际也没有 `--catch-up`**（`install_task.ps1` 源码 .lnk 分支写了、实际部署未生效）→ N-9 补跑机制整体失效。
- **证据**：
  - 计划任务：`schtasks /Query /TN AITrader` → `Task To Run: C:\veighna_studio\pythonw.exe D:\...\ai_trader\run.py`（**无 `--catch-up`**）；`scripts/install_task.ps1` 的 `schtasks /Create` 行（约 L43-44）本就没带该参数；
  - 启动项：`AITrader.lnk` → `Args: "D:\...\ai_trader\run.py"`（**无 `--catch-up`**）；`install_task.ps1` 的 `.lnk` 分支（约 L47-52）写了 `--catch-up`，但**实际部署未生效**——脚本与部署漂移；
  - 计划任务 `Repeat: Disabled`、无"错过即运行"（Missed-run）配置；
  - `run.py:540-548` `--catch-up` 实现存在但无入口调用。
- **影响**：跨周末/节假日/关机/断电/计划任务未触发而漏掉的交易日**永不补跑**；N-9 从"已接入"变为"形同虚设"。
- **修复建议**：① 重新执行 `install_task.ps1`（或手工给计划任务 `/TR` 补 `--catch-up 5`、给 `.lnk` 补参数），并以 `schtasks /Query` 复核；② 给计划任务加"错过则尽快运行"与"Start On Batteries"；③ 修正脚本与部署不一致的根因（如版本管理/幂等安装脚本）。

### 🟡 P1-1 告警链路整体关闭——`notify.enabled=false` 且 webhook 为空

- **现象**：即使 P0-3 回撤告警已在代码层修复，**生产环境整条告警链路未启用**，任何失败/无成交/回撤事件都不会推送。
- **证据**：
  - `config.json`：`"notify": {"enabled": false, "webhook_url": ""}`；`config.py:57` 默认 `enabled: bool = False`；
  - `run.py:620`：`if not settings.notify.enabled or not settings.notify.webhook_url: return` 直接短路；
  - `notify.py::send_notify`：推送失败仅 `logger.exception`，**无重试、无本地留档、无次渠道**，静默降级。
- **影响**："无人值守"实为"无人值守且无人知"——08-10 新浪 DNS 全败、08-13 代理拒绝、账本被重置等关键事件，用户只能靠肉眼看日报/日志发现；若未来开启告警，Webhook 挂掉也会静默。
- **修复建议**：① 配置真实 webhook（Server酱/钉钉/飞书）并置 `enabled=true`；② `send_notify` 失败写本地 `data/notify_fail.log` + 重试 1~2 次；③ 分级推送（P0 必推：跑批失败/库异常/数据陈旧；P1/P2 降噪），避免空仓误报噪音（衔接 P1-7）。

### 🟡 P1-2 无 `--health` 自检、无"last_run 陈旧/账本未演化"监控（P1-2 未落地）

- **现象**：系统没有任何"我是否健康"的自动自检入口；`check_daily.py` 是手动脚本，**未被任何计划任务引用、不返回非 0 退出码、不接告警**。
- **证据**：`run.py` argparse（约 L378-461）无 `--health` 参数；`scripts/` 下无 check_daily 任务；`check_daily.py:10-16` 仅 `print`，无退出码/告警；本次"主库被清空而 last_run 仍 ok=true"即为缺监控的实证。
- **影响**：Key 失效/网络断/任务没跑/库被清空/"整天被剔除/引擎空转"等故障只能人肉发现，无法在影响累积前介入。
- **修复建议**：按 IMPROVEMENTS.md P1-2 建议加 `--health`（网络连通 / 交易日历可加载 / key 非空 / config 一致性 / bars 新鲜度 / last_run 新鲜度 / 各账户最近快照时点 / 账本连续性），返回非 0 码；`check_alerts` 增加 `last_run_stale_days`；挂计划任务每日二次巡检（如 16:30 / 20:00）。

### 🟡 P1-3 P0-4 写路径仍未原子化——决策/留痕可能重复（资金层已被 v0.20 唯一约束兜底）

- **现象**：`_run_engine` 写路径仍是逐条独立连接、无事务包裹；`database.py` 无 `transaction()` 上下文管理器。v0.20 已加 trades 唯一约束 + `INSERT OR IGNORE` + snapshot upsert，使 **trades/state/snapshot 幂等**（资金层基本堵住）；但 `add_decision` 是普通 INSERT（decisions 表无唯一约束）→ 崩溃重跑会**重复插入决策留痕**。
- **证据**：`batch.py:333-366`（`begin_batch_run → add_trade×N → save_state → add_snapshot → complete_batch_run`）；`database.py` grep 仅 `begin_batch_run`（L423），无 `transaction/BEGIN/COMMIT`；`database.py:266-273 add_decision` 为普通 INSERT；`_SCHEMA` 中 decisions 无 UNIQUE；`docs/IMPROVEMENTS.md` L276 明确"完整 `transaction()` 包裹留作后续加固"。
- **影响**：崩溃窗口重跑会重复的决策样本污染 Rank IC 校准 / 归因 / 复盘；部分写盘后重跑的状态叠加在极端 case 下仍可能与 trades 留痕不一致，影响对账。
- **修复建议**：按 P0-4 建议包 `Database.transaction()` 上下文管理器（`with self.db.transaction():` 整体回滚）；短期至少给 decisions 加 `UNIQUE(account_id,date,symbol,action,fallback)` + `INSERT OR IGNORE`。

### 🟡 P1-4 API 成本无累计记账、无预算上限；缓存对每日运行几乎不省（P1-6 未落地）

- **现象**：只有单日 `last_run.api_stats`（calls/cache_hits）计数，无 `api_usage` 累计表、无估算成本、无预算护栏；缓存（819,315 bytes）存在，但 08-13 运行 `cache_hits=0`。
- **证据**：`run.py:587` `api_stats` 仅当日；`database.py` schema 无 `api_usage` 表；`deepseek.py:63-65,215-218` 为进程内计数（缓存未命中才 `api_calls+=1`）；`data/last_run.json` `api_stats: {ai: calls=1, cache_hits=0}`；缓存键含日期/行情/模型/temperature → **跨天必不命中**，仅对同日重试与回测重放省钱。
- **影响**：烧钱总量不可见、无预算上限，成本漂移无法察觉；"缓存省了钱"对每日批处理基本是错觉。
- **修复建议**：新增 `api_usage` 表（date/engine/calls/cache_hits）逐日累计，日报与 `--health` 展示"本月调用/估算成本"；设月度预算，临近阈值告警；若需提升跨天命中率，可评估"仅特征快照"类稳定键（须权衡数据新鲜度）。

### 🟢 P2-1 计划任务电源/登录模式削弱无人值守可靠性

- **现象**：任务属性 `Stop On Battery Mode`、`No Start On Batteries`、`Logon Mode: Interactive only`、`Repeat: Disabled`（错过不补）。
- **证据**：`schtasks /Query /TN AITrader /V` → Power Management / Logon Mode / Repeat 三行。
- **影响**：笔记本电池供电时 15:30 不启动/被停止；未保持登录会话时不跑；错过当天不补——叠加 P0-2（无 catch-up）漏跑概率上升。
- **修复建议**：任务开启 "Start On Batteries"（或取消"电池时停止"）；若为无人值守可考虑"无论用户是否登录都运行"（需服务账户/存储密码，谨慎）；加"错过则尽快运行"。

### 🟢 P2-2 `_maybe_notify` 用 n×2 日历天近似交易日 + 全局 ok 误报（P1-7 未落地）

- **现象**：`cutoff = date - timedelta(days=n*2)`（`run.py:633`）用日历天近似 N 个交易日，长假/周末偏差大；`ok` 为跨引擎全局判定，单引擎失败会让**所有账户**报"批处理失败"。
- **证据**：`run.py:618-641`；IMPROVEMENTS.md P1-7 未落地（当前因 notify 关闭暂无症状，开启即暴露）。
- **修复建议**：用 `is_trading_day` 统计最近 N 个交易日成交；空仓与"有持仓但无成交"（真异常）区分；`ok` 按引擎独立判定。

### 🟢 P2-3 日志对"正常完成/成本/告警结果"覆盖不足 + `last_run` 非原子写

- **现象**：`app.log` 仅 35 行（08-09~08-13），只覆盖异常（拉取失败/`before_close`/日历降级/跳过）与政策条数，**无每日完成摘要、无 API 调用/缓存命中、无告警发送记录、无启动/退出标记**；`write_last_run` 用 `write_text` 直接写（非原子，崩溃可能半写）；`locked` 分支会覆盖运行中实例的 `last_run`。
- **证据**：`data/logs/app.log` 尾部 35 行；`run.py:102` `last_run_path.write_text(...)`；`run.py:485` `write_last_run({"mode": "locked", ...})`。
- **影响**：排查"今天跑没跑成 / 为什么没成交 / 成本多少"缺抓手；极端崩溃下 `last_run.json` 可能损坏或误导。
- **修复建议**：日志每日增加 summary（各引擎 trades/assets/pnl/api 调用、补跑记录、告警结果）；`last_run` 改原子写（`tmp + os.replace`，同 AI 缓存）；`locked` 分支不覆盖进行中实例的状态。

## 3. 做得好的地方

1. **双层防重复可靠**：单实例锁（`lock.py`，OS 文件锁崩溃自动释放、无残留，`run.lock` 仅 1 字节空格）＋ 同日幂等（`batch_runs` 只认 `done` + `has_snapshot` + trades 唯一约束 + `INSERT OR IGNORE`）；日志显示 08-10~08-13 多次同日并发运行均正确跳过、**零重复成交**，且备份库 `batch_runs` 12 条全 `done`、无 `running` 残留。
2. **数据新鲜度守卫扎实**：`bars[-1]==决策日` 硬校验 + 逐标的陈旧剔除 + 收盘守卫（`<15:00` 拒绝结算）+ 日历降级保守跳过 + 行情失败 bars 缓存兜底；真实日志佐证 08-11/08-12/08-13 三次 `before_close` 均正确拦截盘中运行、08-10 DNS 与 08-13 代理失败均有留证。
3. **失败留证 + 重置安全设计**：拉取失败/代理拒绝/日历不可用等关键异常均记 ERROR/WARNING（`data/logs/app.log`），且有 `--force` 逃生通道与备份库（08-13 16:30 前数据完整保存，使 P0-1 可恢复）；**重置后 `_catch_up_dates` 基于快照日期（快照清空 → 返回空 → 不乱补历史）**，`run.py:213-233` 设计正确，避免了重置后误补旧交易日。

---

## 4. 一句话总结

**"每日必跑"的核心链路很稳（锁 + 幂等 + 新鲜度守卫都可靠），但自愈（catch-up 未接线）与可观测（health / 告警 / 成本 / 日志）两翼缺失，且主库账本已被静默重置——无人值守的"稳"掩盖了"无人知"，建议优先补 `--health` + 开启告警 + 修复 catch-up 接线，并给数据库重置立规矩。**
