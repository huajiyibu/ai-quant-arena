# 体检方向 02：账本正确性与数据一致性（诊断结果）

> 检查日期：2026-08-13 · 只读体检（仅 SELECT 验证 + 临时库模拟，未改动 `data/aitrader.db`）
> 检查对象：`aitrader/database.py`、`aitrader/portfolio.py`、`aitrader/batch.py`、`aitrader/attribution.py`、`aitrader/risk.py`、`docs/IMPROVEMENTS.md`，真实库 `data/aitrader.db` 与备份 `data/aitrader_backup_20260813_1630.db`

## 一、结论摘要

1. **当前（重置后）账本完全干净，可放心作为新起点**：三账户 `cash=1,000,000`、`positions` 空、`last_interest_date=None`，`trades/decisions/daily_snapshots/batch_runs` 全为 0，无任何残留；`bars` 缓存 207 根（每标的 69 根，2026-05-08~08-13）合理保留作估值兜底。重置同时消除了 P0-5 的"历史从未计息"缺口（全新起点，无需回填）。
2. **核心账务口径全部一致**：备份中 7 笔成交 `amount` 全部 = `vol×price×(1+0.00025)` 精确匹配（无毛/净口径混用）；归因 `attribute_trades / closed_trade_pairs` 用同一净佣金口径；三账户最新 `state` 与最新快照 `cash+持仓市值=total_assets` 全部相等；08-13 三账户首次计息 = 前日 `cash×0.017/252` 精确匹配，`last_interest_date` 当日幂等生效；`pnl` 明确为**累计口径**（`total_assets - initial_capital`）。
3. **最大风险仍是 P0-4 写路径非原子**（IMPROVEMENTS 自认"完整事务留后续"）：临时库模拟"save_state 已写、快照未写"崩溃后重跑**能自愈**（不重复成交、不双计息、不卡死），但存在 **计息漏计窗口**（marker 先于入账）与 **`--date` 回放改写真实账本** 两个未设防缺口，建议以"跑一天=一个原子事务"一并收口。

## 二、问题清单

### 🔴 P0-1 批处理写路径非原子（IMPROVEMENTS P0-4 未落地）
- **现象**：`_run_engine` 的写路径 `begin_batch_run → add_trade×N → update_decision_execution → save_state → add_snapshot → _calibrate_forward_returns → complete_batch_run` 是**逐条独立连接写库，无事务包裹**；任一步崩溃都会留下"半写"现场（trades 写而 state 未写 / state 写而快照未写 / 快照写而 done 未写）。
- **证据**：`aitrader/batch.py` L333（begin_batch_run）、L351（save_state）、L353（add_snapshot）、L364（complete_batch_run），相互之间无 `BEGIN/COMMIT`；`docs/IMPROVEMENTS.md` L234/L276 明确记录"P0-4 完整事务原子化**未做**，完整 `transaction()` 包裹留作后续加固"。
- **影响**：崩溃重跑的成交幂等虽已被唯一约束 + `already_holding` + `last_interest_date` + N-2 兜住（见"做得好的地方"），但：① 崩溃窗口内的重跑是基于"已成交后"的状态重新做决策（AI 的 prompt 含账户状态 → 当日决策语义被污染，`update_decision_execution` 的 `WHERE execution_result IS NULL` 还会把结果回填到**旧的**决策行而非新行）；② 直接引发 P1-1 利息漏计。**原子性承诺始终未兑现**，是当前账本正确性最大的结构性风险。
- **修复建议**：`Database` 增加 `transaction()` 上下文管理器（`BEGIN IMMEDIATE … COMMIT/ROLLBACK`），把 `begin_batch_run → add_trade → save_state → add_snapshot → complete_batch_run` 整体包进**同一个 SQLite 事务**（任一环节失败整体回滚，重跑从干净状态开始）。

### 🟠 P1-1 计息幂等存在"漏计窗口"——防了双计，没防漏计
- **现象**：`set_last_interest_date(account_id, today_str)`（`batch.py` L298）在 `save_state`（L351）之前约 **53 行**写入。若进程在两者之间崩溃（**引擎 `decide` 网络挂起被 kill 最可能**，其次 add_trade/begin_batch_run），则 `last_interest_date` 已=今日、但 `state` 未入账 → 重跑时 `last_int < today_str` 为 False 直接跳过计息 → **当日利息永久漏计、永不补计**。
- **证据**：`batch.py` L292-298（计息块：`if last_int is None or last_int < today_str: … set_last_interest_date`）→ L307-329（decide + add_decision）→ L333（begin_batch_run）→ L351（save_state）；marker 与入账不同步、跨多步。临时库模拟（崩溃点设在 add_snapshot，即 save_state 之后）确认入账不丢，但代码行序证明 save_state **之前**的窗口真实存在。
- **影响**：每账户每崩溃日漏计约 0.67~60 元（1,000,000×0.017/252≈67.46，持仓后基数更小），崩溃越多偏差越大，与"逐日复利"口径产生系统性偏差；这正是体检重点怀疑的"`last_interest_date` 在崩溃窗口是否真的防双计"的答案——**防双计成立，但引入了漏计**。
- **修复建议**：把 `set_last_interest_date` 移到 `save_state` **之后**（与状态同事务提交），或直接随 P0-1 的 `transaction()` 一起原子提交；理想上计息与状态同一事务。

### 🟠 P1-2 `--date` 回放会改写真实账本——`source` 只标记、不拦截
- **现象**：`--date <过去>` 在**无快照**的账本上（如刚重置的干净账本）会直接执行：`_run_engine` 照常 `save_state`（改当前 `state`）与 `add_snapshot`（写历史快照）；对**已有真实快照**的日期加 `--force` 时，`add_snapshot` 的 `ON CONFLICT(account_id,date) DO UPDATE` 会**覆盖真实快照**的 `cash/total_assets/pnl/bar_date`，且 `source` 不更新（real 仍标 real，无法察觉）。
- **证据**：`database.py` L362-372 `add_snapshot` 冲突分支只更新 `bar_date/cash/total_assets/pnl`（`source`/`interest` 不更新）；`run.py` L557 `runner.run(date, force=args.force)` 无 source 守卫；`batch.py` L349-361 回放路径与实时路径共用同一 `save_state + add_snapshot`，无只读/隔离分支。
- **影响**：在用户刚清零的干净账本上回放历史日期，会**注入虚假的历史成交/快照并改动实时 state**（`last_price` 回退到历史价，若回放触发不同决策现金也会变）——精心维护的"干净起点"被污染，且 `source` 标记无法识别覆盖过的真实快照。
- **修复建议**：回放模式改为**只读执行**（不 `save_state`、不落库，或写独立 replay 库/临时库）；或 `add_snapshot` 对已存在 `source='real'` 的快照拒绝被 replay 覆盖（replay 不覆盖 real）。

### 🟡 P2-1 `reset_account` 未清 `batch_runs`
- **现象**：`reset_account`（`database.py` L390-405）只删 `trades/decisions/daily_snapshots` + 清 `last_interest_date`，**不 DELETE `batch_runs`**。
- **证据**：`database.py` L390-405 无 batch_runs 删除语句；本次手动重置是**额外**执行了 `DELETE batch_runs` 才达成当前 `batch_runs=[]`（当前库查询佐证：`batch_runs` 为空、`trades/decisions/snapshots` 全 0）。
- **影响**：若后续直接用 `reset_account` 重置每日账本（而非手工补删），历史 `done` 标记残留 → `has_batch_run`（只认 done，L439）会挡住同日期重跑并误判"该日已处理"，需 `--force` 才能重跑。
- **修复建议**：`reset_account` 一并 `DELETE FROM batch_runs WHERE account_id=?`（并建议同步清 `last_interest_date`，当前已清）。

### 🟡 P2-2 `--force` 重跑产生重复 decisions 行（留痕不幂等）
- **现象**：`decisions` 表**无唯一约束**，`add_decision`（`database.py` L291）无条件 `INSERT`；`--force` 重跑同日会插入同 `(date,symbol,action)` 新行。成交因唯一索引幂等，但**决策留痕翻倍**、AI 引擎会被再次调用并**重新计费**。
- **证据**：`database.py` L291 `add_decision` 无 `ON CONFLICT`；`_SCHEMA` 中 `decisions` 无 UNIQUE；`docs/IMPROVEMENTS.md` L198 记录"--force 幂等重定义（清当日留痕再跑 / upsert）未做"。
- **影响**：审计留痕膨胀；`get_uncalibrated_buys` / 日报"今日决策明细" / Rank IC 可能被重复行干扰；`--force` 触发 AI 重新调用、成本翻倍。
- **修复建议**：落地 IMPROVEMENTS 的"--force 幂等重定义"：force 时先删当日该账户 decisions（或按 `(date,symbol,action)` upsert）再留新痕。

### 🟡 P2-3（澄清，非独立缺陷）`add_snapshot` 冲突分支不更新 `interest`/`source`
- **现象**：`ON CONFLICT(account_id,date) DO UPDATE` 不更新 `interest`/`source`（`database.py` L366-371）。
- **证据**：同上行号。
- **影响**：`interest` **不更新恰巧是正确设计**（force 重跑计息被跳过、`interest_today=0`，若更新反而会把首轮利息清零）；但 `source` 不更新是 P1-2 的组成部分（replay 覆盖 real 后 source 失真）。
- **修复建议**：`interest` 保持不动（正确）；`source` 语义随 P1-2 修复解决。

## 三、做得好的地方

1. **幂等防线组合有效且被实证**：trades 唯一索引 + `INSERT OR IGNORE`（P0-1）+ `already_holding` 风控（P1-2）+ `last_interest_date` + N-2（`batch_runs` 只认 done）。临时库模拟"`save_state` 已写、`add_snapshot` 未写"崩溃后自动重跑：**不重复成交、不双计息、快照补齐、引擎不卡死**，且重跑后 `cash+市值=total_assets` 恒等式仍成立——崩溃窗口的重复记账风险已实质兜住。
2. **佣金/记账口径全局一致**：备份 7 笔成交 `amount` 全部 = `vol×price×(1+0.00025)` 精确匹配（rule 08-10 两笔、08-12 一笔、ai/ai_policy 四笔均验证）；`attribute_trades / closed_trade_pairs` 用同一净佣金口径（`卖价×(1-c) − 买价×(1+c)`），与成交流水完全一致，无毛/净混用。
3. **重置后账本彻底干净**：三账户 `cash=1,000,000`、无持仓、无 `trades/decisions/snapshots/batch_runs` 残留、`last_interest_date=None`；`bars` 缓存合理保留；明天 15:30 起从全新起点逐日计息（约 67.46 元/日/账户），口径一致可复算。

## 四、一句话总结

**账本口径与幂等防线扎实（成交/利息/快照/归因四口径一致、重置干净、崩溃重跑不重复记账），剩余风险集中在三处——写路径非原子、计息 marker 先于入账、`--date` 回放不设防——本质是同一件事，把"跑一天"做成一个原子事务即可一并收口（P0-4）。**
